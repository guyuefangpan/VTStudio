Vela 快应用开发

从需求拆解到真机验证，为小米手环、手表等 Vela 设备交付能跑、能维护的快应用，连同源码、安装包与技术文档一并交付。

覆盖哪些应用类型

Vela 设备算力与内存有限，不是所有想法都适合落地。下面是我们确认能做的类型与各自的约束条件。

表盘类数字表盘、指针表盘、自定义绘制表盘。重点处理常亮显示与息屏功耗，避免高频重绘。
工具类计算器、计时器、单位换算、待办、日程提醒。逻辑简单但要求交互跟手。
健康类步数、心率等数据的展示与本地记录。受系统权限限制，仅能调用官方开放的接口。
轻游戏休闲小游戏。受内存与算力约束，需要控制资源体积与帧率预算。
信息聚合天气、日程、快捷设置等一屏展示类应用，重点是数据刷新策略与省电。

用到的技术栈

应用框架Vela 快应用框架，页面由模板、样式与脚本三部分组成。
开发语言JavaScript（应用层）；涉及底层能力时使用 C。
界面实现官方 UI 组件为主，标准组件无法满足时自绘。
开发工具AIoT-IDE 与 Vela 官方工具链，配合真机调试。
调试手段真机日志、性能面板、设备信息读取（分辨率、DPR、系统版本）。

交付物清单

项目结束时你会拿到这些，不会出现"只有安装包、没有源码"的情况。

  1. 完整源码：包含注释与目录说明，可直接二次开发。
  2. 可安装包：构建产物，可直接部署到设备验证。
  3. 技术文档：目录结构、构建步骤、关键接口与数据结构说明。
  4. 真机测试报告：覆盖启动耗时、内存峰值、交互帧率等实测数据。

性能上我们盯哪些指标

小屏穿戴设备对性能格外敏感，这几项是我们验收前的必查项。

冷启动耗时从点击图标到首屏可交互的时间，尽量压缩初始化与资源加载。
内存占用控制在设备可用预算内，避免后台被系统回收。
交互帧率滑动、切换等场景保持流畅，避免掉帧与卡顿。
功耗表现常亮、定时刷新、传感器采样频率都会单独评估。

明确不做的部分

提前说清楚边界，避免后期返工。

我们不做需要系统级签名或 root 权限的功能，不做绕过官方分发与审核限制的能力，也不承接涉及用户隐私数据采集的需求。如果你的需求落在这些范围里，沟通阶段就会直接告诉你。

技术咨询与培训

面向已经有开发能力的团队：把 Vela 平台的开发方法、调试手段与踩坑经验传递过去，而不是替你把活干完。

培训内容

按模块组织，可以整套走，也可以只挑需要的部分。

环境搭建工具链安装、模拟器配置、真机调试通道打通。
框架入门应用目录结构、生命周期、页面路由与参数传递。
界面开发布局模型、样式写法、组件使用、多分辨率适配。
能力调用传感器、本地存储、网络请求、蓝牙通信。
性能与上架常见性能问题定位、打包签名、上架流程与审核注意事项。

培训形式

线上直播分次进行，每次留出实操与答疑时间。
录播 + 材料适合团队自行安排进度，可反复回看。
企业内训按团队现有项目情况调整案例与重点。

技术咨询服务

针对具体项目的问题，给出可执行结论。

  1. 架构评审：目录结构、状态管理、模块划分是否合理，输出问题清单与修改建议。
  2. 性能诊断：定位卡顿、内存增长、异常耗电的具体原因，而不是泛泛而谈。
  3. 技术选型：框架、组件、第三方库的取舍，结合你的目标机型给出结论。
  4. 疑难排查：特定机型上的兼容问题、构建失败、签名异常等。

你会拿到什么

  • 培训课件与示例代码（可保留用于内部复用）
  • 评审或诊断报告（问题清单 + 优先级 + 修改建议）
  • 沟通期内的问题答疑

项目制外包

需求能说清楚、希望按约定时间拿到成品时，用这种方式。我们按阶段推进，每个阶段都有可以验收的东西，不是到最后才给你看结果。

什么情况适合走项目制

  • 功能范围能够事先界定清楚
  • 有相对明确的交付或上线时间
  • 希望最终拿到完整源码与文档，可以自己维护
  • 过程中不需要频繁改变方向

阶段与对应产出

每一阶段结束你都能看到实物，不是口头汇报进度。

需求梳理输出需求清单与功能边界说明，双方书面确认后进入下一阶段。
方案与报价输出技术方案、工期拆解与费用明细，确认后再启动。
开发实现按里程碑提交可运行版本，你能随时在真机上体验当前进度。
联调测试在目标机型上完成验证，输出测试报告与遗留问题清单。
交付维护交付源码、文档与构建说明，并包含约定时长的维护支持。

关于报价与变更

把规则说在前面，避免后期互相扯皮。

  1. 按项目评估：依据功能复杂度与工期整体报价，不按小时计费。
  2. 分阶段支付：具体比例与节点在方案确认时写明。
  3. 需求变更：走补充确认流程，会同时告知对工期与费用的影响，不会先做后谈。

两点提醒

需求描述得越具体，报价与工期就越准；中途中大范围改需求一定会影响交付时间，我们会提前把影响范围告诉你，由你决定是否调整。

适合自己有开发力量、但希望有人在关键节点把关的团队。我们不替代你写代码，而是在你做决策时给出有依据的判断。

具体包含什么

日常答疑开发过程中遇到的技术问题，通过约定渠道提出并得到回复。

合作形式

按周期以月为单位，约定沟通频次与响应时效。
按次针对单次评审、诊断或答疑，适合需求不连续的团队。

和项目制外包的区别

两张表说清楚，方便你判断该选哪个。

谁写代码顾问模式是你的团队写；外包模式是我们写。

联合开发

面向需要长期迭代的产品：双方共同投入，按约定分享成果。这不是外包关系的变体，合作前提比报价更重要。

我们会在什么情况下考虑

  • 产品方向清晰，且有持续迭代的价值
  • 需要长期投入而非一次性交付
  • 你希望深度参与决策，而不是甩手等结果
  • 双方对投入与分配能达成书面一致

我们投入什么

开发人力承担约定的开发任务与排期责任。
技术积累已有的组件库、调试工具与工程脚手架可直接用于项目。
测试环境自有设备用于真机验证，覆盖主流机型。
文档沉淀过程中的设计决策与踩坑记录整理成文档。

需要你提供什么

产品方向明确的目标用户与功能优先级，避免反复改方向。
决策效率关键问题能快速拍板，沟通链路要短。
配套资源设计、运营、资质、服务器等我们无法覆盖的部分。

合作前提

这几条不满足的话，我们会直接说明不适合。

联合开发需要签署书面协议，明确知识产权归属、投入比例与收益分配。我们不参与方向摇摆、决策链条过长的项目——这类合作通常双方都会失望。有意向可以先从一次小规模的项目制合作开始，彼此验证配合度。

系统与驱动适配

涉及系统层的工作：驱动移植、系统裁剪、板级适配与功耗调优。这类项目的周期通常长于应用开发，前置条件也更多。

具体做什么

驱动适配传感器、屏幕、通信模组等外设的驱动移植与调试。
系统裁剪按硬件资源裁剪内核与系统组件，控制固件体积与内存占用。
板级移植将系统移植到新的硬件平台，完成最小系统启动。
功耗调优休眠策略、外设电源管理、唤醒源配置。
启动优化缩短从上电到可用状态的时间。

涉及的技术栈

操作系统NuttX RTOS 及其上的 openvela 系统层。
开发语言C，少量汇编（启动与上下文切换相关部分）。
构建系统基于 Kconfig / Makefile 的配置与编译体系。
调试手段串口日志、JTAG 调试、逻辑分析仪（硬件问题定位）。

交付物

  1. 驱动源码：包含适配说明与关键寄存器/配置注释。
  2. 可烧录固件：能在目标硬件上启动并跑通验证项的镜像。
  3. 测试报告：覆盖功能验证、稳定性与功耗实测数据。
  4. 移植文档：便于后续在其他硬件上复用。

安装与启动安装包能否正常部署、冷启动耗时、异常退出的复现路径。
界面适配不同分辨率、圆形屏与方形屏下的布局是否错位、文字是否截断。
交互响应触摸、滑动、物理按键的响应是否符合预期。
传感器与权限数据能否正常读取、采样频率是否合理、权限申请是否合规。
稳定性长时间运行、前后台切换、低电量场景下的表现。
功耗表现常亮显示、后台刷新、传感器持续采样的耗电情况。

怎么测

  1. 逐台验证：每款机型单独跑，不根据一台机器的结果推断其他机型。
  2. 记录实测数据：启动耗时、内存峰值等用数字记录，写进测试报告。
  3. 问题不藏着：发现的遗留问题会列成清单交付给你，而不是等你自己发现。

关于"适配"这个说法

把话说明白，避免误解。

上面列出的机型是我们日常开发与验证会覆盖的范围，但不同机型的验证深度并不完全一致——常用机型验证最充分，较新或较少使用的机型以核心功能验证为主。如果你关心的机型不在这个列表里，可以先沟通：有设备我们就直接测，没有设备则需要你提供样机后才好下结论。我们不会在没有实测的情况下声称"已完成适配"。
